# Service worker: what it caches, and how updates reach people

Generated by Workbox from `workbox-config.js` when you run `npm run build:web`.
Output lands in `dist/`, with the worker at `dist/sw.js`.

## Served under /atiokb-webapp

The app lives at `https://sti-portal.fao.org/atiokb-webapp`, so everything is
under that path: `expo.experiments.baseUrl` in `app.json` prefixes the bundle and
assets, `public/index.html` and `public/manifest.json` name the manifest, icons
and worker with it, and the worker is registered as `/atiokb-webapp/sw.js` with
scope `/atiokb-webapp/` — it never sees the rest of the portal. Its navigation
fallback is `/atiokb-webapp/index.html`, so a refresh or a deep link anywhere
under the path gets the app shell.

`npm run build:web` clears the bundler cache (`expo export --clear`). Without it
a changed `EXPO_PUBLIC_*` value — `EXPO_PUBLIC_DATA_SOURCE` especially — is not
picked up: a "jsonapi" rollback build was measured still reading Supabase.

## What it caches

The **app shell only**: HTML, JavaScript, CSS, icons, the manifest, and the
fonts the icon set needs. Enough to render the frame with no network.

**Never the 37 MB catalogue.** Decision D9 fixes that for Phase 1, and
`globIgnores` excludes `**/*.db` so it stays true even if the export changes.

So offline, the app opens and explains that it cannot reach data. It does not
browse, search or show saved records. Full offline data is explicitly out of
Phase 1 scope.

## Update policy

**A new build takes over on the next fresh load.**

The config deliberately does *not* set `skipWaiting` or `clientsClaim`. When
someone has the app open and a new version is deployed, the new worker installs
in the background and waits. It activates the next time the app is opened from
scratch — not under a page someone is currently using, where swapping scripts
and styles mid-session can look broken.

`cleanupOutdatedCaches` is on, so activating deletes the previous version's
files rather than leaving them to accumulate.

### Why this and not immediate takeover

Expo warns that a badly versioned service worker can pin people to a stale build
with no way out — and unlike a phone app, there is no app store update to clear
it. The risk being avoided is *permanently* stale, not *briefly* stale.

This policy cannot strand anyone: nobody keeps an old build beyond their next
fresh visit. For the WFF booth, where each visitor opens the URL once from a QR
code, every visitor gets the current build.

The cost is that someone who keeps a tab open through a deploy continues on the
old version until they reopen. That is the intended trade.

### If you ever need an instant rollout

Add `skipWaiting: true` and `clientsClaim: true` to `workbox-config.js`. Do it
knowingly: open pages will swap assets underneath whoever is using them.

## The catalogue data source

With `EXPO_PUBLIC_DATA_SOURCE=supabase` the catalogue comes from Supabase RPCs
and the worker caches none of them: IndexedDB already holds the full index, the
vocabularies and saved records (see OFFLINE-STORAGE.md), and a second cache of
the same data would only be a second thing to go stale. The `/jsonapi`
stale-while-revalidate rule (OFFLINE-STORAGE.md, "The service worker's share")
stays, because the portal path is the default and the rollback route.

## Testing it

```sh
npm run build:web
npm run serve:web       # dist/ under http://localhost:8090/atiokb-webapp/
```

`serve:web` mounts the build at the same path the portal will, so the base
path, deep links and the worker's scope are tested as deployed. Then in Chrome:
load the page once, DevTools → Network → **Offline**, reload.
The shell should appear. DevTools → Application → Service Workers shows its
state, and **Unregister** there is the reset button while developing.

The worker is **not** registered on the Metro dev server (`expo start --web`,
port 8081), so day-to-day development is unaffected and cannot serve you a
cached build.
